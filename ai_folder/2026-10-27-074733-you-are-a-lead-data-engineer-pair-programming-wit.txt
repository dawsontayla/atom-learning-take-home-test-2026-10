> explain the purpose for establishing 'epoch-like' values

● Epoch-like values are a common sign of a broken timestamp. Unix time starts at
  1970-01-01 00:00:00 UTC, and the check counts anything before 1970-01-02.

  Why they show up
  - Zero or null coerced to 0: an upstream system or ingestion step writes 0 (or
    an empty or failed value) into a numeric epoch field. It then converts to
    1970-01-01. This is the most common cause. The value is really "missing",
    but it looks like a valid date and slips past a null check.
  - Unit mix-ups: a seconds value read as milliseconds, or the reverse. Seconds
    treated as milliseconds land within days of 1970, for example 1.7e9 ms is
    about 20 days after the epoch. Milliseconds treated as seconds land far in
    the future, which the n_future check catches.
  - Default or placeholder values: some sources use 1970-01-01 as a "no date"
    sentinel, just as others use 1900-01-01 or 9999-12-31.

  Why it gets its own count
  These values hide from other checks:
  - The null profile in section 2 counts them as populated.
  - Any min() on the column gets dragged to 1970, which distorts the date range.
  - Duration calculations, such as time between sitting start and end, will be
    off by about 56 years.
  - They would silently fall into the n_before_2000 bucket, which could be
    mistaken for genuine old data. Keeping a separate count tells you whether
    early dates come from this sentinel pattern or from real historical records.

  Why the threshold is 1970-01-02
  It's a day, not an exact match on the epoch instant. That also catches values
  that landed on 1970-01-01 after a timezone shift. A real record from 1970 is
  implausible for this dataset, so false positives should be negligible.

  Overlap: every epoch-like row is also counted in n_before_2000, so
  n_epoch_like is a subset of it. If n_epoch_like is non-zero, the next step is
  to look at the raw rows to see whether the source stores 0, null, or a string.

  Data engineering and long-term points
  - True point-in-time snapshots. Your current pipeline filters on event time
    only, and it reads soft-deletes and sitting status as they are today. A
    snapshot re-run for an old date can therefore differ from what you would
    have seen then, which is a quiet look-ahead leak.

      happened, so snapshots can be rebuilt as-known-at.

  - Scores are versioned and reproducible. Your 80–120 scale is a proprietary
    approximation of the official one. Store raw_percentage alongside the score
    and keep the conversion in a versioned config table, so a formula change
    doesn't silently rewrite history. You already list the config table under
    more time.
  - Targets that survive grade boundary changes. Predict a relative measure,
    such as percentile or residual against expectation, then map it to a grade.
    Boundaries shift every year.
  - Output you can audit.
    - Predictions should be a distribution with credible intervals, not a single
      grade.
    - Write them to a partitioned table that carries model_version and
      run_timestamp, like your score table.
